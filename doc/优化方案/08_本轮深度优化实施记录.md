**改动 2：修 `atomic_write` 的两个真实缺陷**（`src-tauri/src/atomic_write.rs`）

- **缺陷 A：临时文件名只带 pid，同进程并发写同一文件会互相截断**（`atomic_write.rs:41` → 改为 `atomic_write.rs:131` 的 `temp_path_for`）
  - 原临时名 `.{name}.{pid}.tmp`：**同一次进程内的每次调用完全相同**。
  - 自动保存与手动保存撞在一起时：后一次 `File::create` 截断前一次写好的内容，
    前一次 `rename` 走掉的是**后一次**的内容，后一次 `rename` 报 ENOENT。
    症状是「保存偶发失败」+「落盘内容不是自己写的那份」——**数据安全问题**。
  - 修法：临时名加自增序号 `.{name}.{pid}.{seq}.tmp`（`TMP_COUNTER`，`atomic_write.rs:14`）。
    Windows 的 `.bak` 同理（`atomic_write.rs:64`）。
  - 副作用检查：临时名仍以 `.` 开头 → `watcher.rs:106` 的过滤器（`starts_with('.')`）仍会过滤掉，不会触发「文件被外部修改」。

- **缺陷 B：失败路径不清理临时文件**（`atomic_write.rs:48-73`）
  - 原实现：`File::create` / `write_all` / `sync_all` / `rename` 任一步失败，临时文件**留在用户笔记目录里**。
  - 临时文件既不是笔记、又被文件树与搜索忽略 → 用户看不见也删不掉。
  - 修法：每条失败分支都 `remove_file(&tmp)` 后再返回错误；**错误文案保持原样**（前端 `mustSucceed` 依赖它）。

**改动 3：加看门狗测试**（`src-tauri/src/atomic_write.rs:408` `no_bare_fs_write_outside_atomic_write`）

- 扫描 `CARGO_MANIFEST_DIR/src/**/*.rs`，除 `atomic_write.rs` 外，
  任何一行出现 `fs::write(` 或 `File::create(` 即失败。
- 扫描前先剥注释（正确识别字符串字面量里的 `//`），所以注释里提到 `fs::write` 不会误报。
- **这条测试不是摆设** —— 植入一个违规文件后它确实会红：

```

}
EOF
$ cargo test --lib no_bare_fs_write

以下写入点绕过了原子写：
/…/src-tauri/src/_guard_probe.rs:3: 出现裸写盘调用 `fs::write(`，请改用 atomic_write / atomic_write_str
test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 65 filtered out
```

（探针文件已删除，`src/` 现存 8 个 `.rs`：`atomic_write.rs` `bench.rs` `commands.rs` `extract.rs` `index.rs` `integration_tests.rs` `lib.rs` `main.rs` `watcher.rs` 之外无残留。）

## 三、T4-05 `useKeyboard` hook

### 3.1 做了什么

新增两个文件 + 抽一个表：

| 文件 | 作用 |
|---|---|
| `src/lib/keyboardShortcuts.ts` | **纯逻辑**（无 React、无 DOM 依赖）：`KeyboardShortcut` 类型、`matchesShortcut`、`resolveShortcut`、`attachKeyboardShortcuts` |
| `src/hooks/useKeyboard.ts` | **React 包装**：`useKeyboard(shortcuts, options)`，挂载/卸载交给它 |
| `src/lib/appShortcuts.ts` | **应用级快捷键表**（21 条），`createAppShortcuts(actions)` 返回 `KeyboardShortcut[]` |

**不是「在旁边另加一个没人用的 hook」** —— 现有代码真的改用了它，三处：

| 位置 | 改造前 | 改造后 |
|---|---|---|
| `src/App.tsx:1682-1724` | 99 行的 `window.addEventListener('keydown', …)` if/else 链 | `useMemo` 出一张表 → `useKeyboard(keyboardShortcuts)` |
| `src/components/SettingsDialog.tsx:59-75` | 自己的 `useEffect` + `window.addEventListener` | `useKeyboard(escapeShortcuts, { enabled: open })` |
| `src/components/FolderContextMenu.tsx:61-78` | 自己的 `useEffect` + `window.addEventListener` | `useKeyboard(escapeShortcuts)` |

`src/App.tsx` 行数 2260 → 2222。

### 3.2 为什么把表也抽到 `lib/`

`useMemo` 的工厂函数是**渲染期**执行的，而表里的 handler 要用
`menuActionsRef`（`App.tsx:1762`）、`reopenTabRef`（`App.tsx:1242`）、`handleSaveRef`（`App.tsx:252`）
这些 ref —— 放在这些声明之前会踩 TDZ（`ReferenceError`）。
所以快捷键表整体挪到了 `menuActionsRef` 声明之后（`App.tsx:1682`），
并在原位（`App.tsx:1001`）留了指引注释。

抽到 `lib/appShortcuts.ts` 的额外好处：**表变成纯数据，可以直接单测**，
不必为了测它去搭 React 渲染环境（本仓不装 testing-library，且本轮禁止新增依赖）。

### 3.3 语义逐条对齐（改造前 → 改造后）

`App.tsx` 原来那条链的全部 21 个分支，连同**看起来不严谨但必须保留**的历史行为，
都 1:1 搬进表里（顺序即优先级，命中即止）：

- `e.key` 统一转小写再比 → `matchesShortcut`（`keyboardShortcuts.ts:55`）
- `cmd = metaKey || ctrlKey` → `isCmdPressed`（`keyboardShortcuts.ts:52`）
- 一次按键只命中一条 → `resolveShortcut` 取第一条命中（`keyboardShortcuts.ts:79`）
- 命中先 `preventDefault` 再执行 handler → `attachKeyboardShortcuts`（`keyboardShortcuts.ts:102`）
- **Esc 那一支不 `preventDefault`** → 表里显式写 `preventDefault: false`（`appShortcuts.ts:126`）
- `cmd && key === 'b'` 没排除 Shift → Cmd+Shift+B **也**切侧栏
- `cmd && key === 'n'` 没排除 Shift → Cmd+Shift+N **也**新建笔记
- `cmd && e.code === 'Backslash'` 没排除 Shift → Cmd+Shift+\ **也**切分屏

后三条是**故意保留的现状**（收紧它们属于行为变更，不在 T4-05 范围内），
但写进了测试，以后真要改，那里就是该改的地方。

### 4.2 写测试时发现的实测行为（与直觉不符，已按实测钉住）

写用例时踩到三处「以为是 A、实测是 B」，都按**实测**写断言并注明原因：

1. `extOf(".gitignore")` 返回 `"gitignore"` 而不是 `""` —— 实现按「最后一个点」取扩展名，不特判隐藏文件

### 4.3 公共装载器 `tests/helpers/hooks.ts`

Node 的 ESM 解析器**不做扩展名补全**，而仓里是 Vite 风格的无扩展名相对导入

（同 `tests/frontmatter.test.ts` 的既有做法）。

> 踩坑记录：钩子**必须同步返回**。写成 `async` 会让 Node 的同步加载路径拿到

## 五、T5-05 性能基准

### 5.1 用等价方式替代了 criterion —— 理由

**criterion 是 crates.io 的新依赖，本轮硬约束是「不得引入新的 npm / crates.io 依赖」，所以没用。**
改用仓内**已有依赖**（`node:test` + `cargo test`）能跑的等价方式：
**「测试 + 阈值断言」**。

| 维度 | criterion | 本轮采用的等价方式 |
|---|---|---|
| 度量对象 | 同一批被测函数 | 同一批（索引构建 / 全文搜索 / 大文件读写 / 大文件前端解析） |
| 可复跑命令 | `cargo bench` | `cargo test --lib bench -- --nocapture` / `npm test` |
| PASS/FAIL | 回归检测 | 阈值断言，红了就是回归 |
| 差别 | 多次采样的统计基线 + 置信区间 | **单次测量 + 硬阈值** |

阈值口径：Rust 侧按**本机实测值 × 5~10 倍**（有 fsync / IO 抖动），
前端侧按 **× 30~150 倍**（纯 CPU 逻辑，无 IO 抖动）。
阈值定太紧会让 CI 变成随机红灯，那比没有基准更糟。

## 八、本轮新发现的问题

1. **`atomic_write` 同进程并发写同一文件会互相截断**（已修，`atomic_write.rs:41`→`131`）。
   临时名只带 pid ⇒ 同一次进程内每次调用的临时路径**完全相同**。
   自动保存与手动保存撞车时，落盘内容与调用方预期不符，且后一次保存被报成失败。
   这是**本轮最实的一个数据安全发现**。
2. **`atomic_write` 失败路径不清理临时文件**（已修，`atomic_write.rs:48-73`）——
   失败一次就在用户笔记目录里留一个看不见、删不掉的垃圾文件。
3. **`App.tsx` 的快捷键表里有 3 条「看起来不严谨」的历史行为**（Cmd+Shift+B / N / `\`）。
   本轮**保留现状**并写进测试，但值得产品侧决策是否收紧。
4. **`tsconfig.json` 的 `include` 只有 `["src"]`** —— `tests/` 目录**不在类型检查范围内**。
   本仓既有如此，新加的测试文件同样不受 `tsc --noEmit` 覆盖（`npm test` 靠
   `--experimental-strip-types` 运行，类型错误不会在 CI 里被拦住）。这是个结构性缺口，
   建议后续把 `tests/` 纳入一个单独的 tsconfig 并在 CI 里检查。
5. `src/lib/frontmatter.ts` 的 `mergeFrontmatter` 在 `src/` 里**零调用方**
   （既有 `tests/frontmatter.test.ts` 已记录该事实，本轮复核确认）。
