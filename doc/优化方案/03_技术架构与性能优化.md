## 一、编辑器选型与性能

### 1.1 当前选型评估

| 维度 | 现状 | 评价 |
|------|------|------|
| 引擎 | Tiptap v3 (ProseMirror) | ✅ 成熟、扩展丰富、社区活跃 |
| Markdown 序列化 | `@tiptap/markdown` | ✅ 双向转换 |
| 自定义扩展 | 16 个（WikiLink/Tag/Mermaid/Fold/Embed/MultiCursor 等） | ✅ 功能完整 |
| 大文档性能 | 未优化 | ⚠️ ProseMirror 全量 DOM，>50KB 文档可能卡顿 |

**结论：保留 Tiptap，不迁移。** 迁移成本远大于收益。优化方向为大文档分块渲染和惰性解析。

### 1.2 大文档优化策略

| 策略 | 说明 | 预期收益 |
|------|------|----------|
| 虚拟化渲染 | 仅渲染视口 ± 2 屏的 ProseMirror 节点 | 10x DOM 节点减少 |
| 惰性 Mermaid/KaTeX | 非视口内的图表/公式延迟渲染 | 首屏 -500ms |
| Markdown 解析 Web Worker | `setContent(content, {contentType:'markdown'})` 移入 Worker | 主线程不阻塞 |
| 增量统计 | `updateStats` 仅在可视区域变化时重算 | 减少 300ms debounce 开销 |

### 1.3 编辑器状态缓存

当前 `Editor.tsx` L174 限制缓存 10 个状态。  
**建议**：  
- 缓存上限提升至 `min(openTabs.length, 30)`  
- 使用 LRU 淘汰而非 FIFO  
- 缓存 EditorState 的序列化 JSON（而非完整 view.state），减少内存占用

## 二、大笔记库索引与增量搜索

### 2.1 当前瓶颈

```
search_in_files (commands.rs L689-739)
  └─ 递归遍历所有 .md → 逐文件 read_to_string → 逐行 find()
  └─ 时间复杂度: O(文件数 × 平均行数 × 查询长度)
  └─ 1000 篇 × 200 行 ≈ 200K 行扫描，预估 3-8 秒
```

### 2.2 推荐方案：SQLite FTS5

```
┌─────────────────────────────────────────────┐
│  Rust 侧 (src-tauri)                        │
│                                             │
│  notes_index.db (SQLite + FTS5)             │
│  ├─ notes(path, title, mtime, tags, links)  │
│  ├─ notes_fts(title, content) USING fts5    │
│  └─ 增量更新: file watcher → upsert/delete  │
│                                             │
│  新 commands:                                │
│  ├─ search_notes(query, filters, page)      │
│  ├─ rebuild_index(dir)                      │
│  └─ index_status() → {total, indexed, stale}│
└─────────────────────────────────────────────┘
```

**IPC 契约建议**：

```typescript
// 搜索请求
interface SearchRequest {
  query: string;           // 支持 "精确" tag:#xxx path:folder/ 正则
  dir: string;             // 笔记库根目录
  page?: number;           // 分页，默认 0
  pageSize?: number;       // 默认 50
  sortBy?: 'relevance' | 'modified' | 'title';
}

// 搜索响应
interface SearchResponse {
  matches: Array<{
    filePath: string;
    title: string;
    snippet: string;       // 含 <mark> 高亮
    line: number;
    score: number;
  }>;
  total: number;
  page: number;
  indexAge: number;        // 索引更新时间戳
}
```

### 2.3 增量索引策略

| 触发 | 动作 |
|------|------|
| 打开文件夹 | 全量扫描，对比 mtime，仅更新变化文件 |
| 文件保存成功 | upsert 单条记录 |
| 文件删除/重命名 | delete + insert |
| file watcher 事件 | 同上 |
| 手动重建 | `rebuild_index` 清空重来 |

**预期指标**：1000 篇笔记全量索引 < 5s；增量单文件 < 10ms；搜索响应 < 200ms。

## 三、知识图谱增量更新

### 3.1 当前问题

`refreshKnowledgeIndex` (App.tsx L437-482) 每次保存后调用 `read-all-notes`，Rust 侧递归读取全部 .md 并解析 title/tags/links。

### 3.2 增量方案

```
保存成功 → emit('note-updated', {path, title, tags, links})
         → 前端仅更新 graphNodes/graphLinks 中对应节点
         → 无需重新读取全部文件
```

**实现要点**：
- Rust `write_file` 成功后，解析该文件的 title/tags/links，通过 Tauri event 推送
- 前端维护 `Map<filePath, NoteSummary>`，收到事件后局部更新
- 打开文件夹时仍做一次全量加载（初始化）
- 删除/重命名时推送 `note-removed` / `note-renamed` 事件

**预期收益**：保存后图谱更新从 O(N) 降至 O(1)，消除大库卡顿。

## 四、附件存储与内存

### 4.1 当前问题

`read_file_binary` (commands.rs L1033-1038) 将整个文件读入内存再 base64 编码返回。  
50MB PDF → ~67MB base64 字符串 → WebView 内存峰值 > 200MB。

### 4.2 推荐方案

| 文件类型 | 策略 |
|----------|------|
| 图片 < 5MB | 保持 base64（简单可靠） |
| 图片 ≥ 5MB | 使用 Tauri `convertFileSrc` 生成 asset:// URL，WebView 直接加载 |
| PDF/视频/音频 | 一律使用 asset:// 协议流式加载 |
| DOCX/XLSX | 分片读取或仅提取元信息 |

**Tauri asset 协议配置**：
```json
// tauri.conf.json → app.security
"assetProtocol": {
  "enable": true,
  "scope": ["$HOME/Documents/**", "$HOME/.z-note/**"]
}
```

### 4.3 图片存储优化

当前 `save_image` 保存到 `~/.z-note/notes/images/`（全局目录）。  
**建议**：保存到笔记同级 `{note_dir}/assets/`，使用相对路径引用，笔记移动时自动迁移。

## 五、数据模型与迁移

### 5.1 当前数据模型

```
Note (前端 types/index.ts)
├─ id: string (文件路径或 note-{timestamp})
├─ title: string
├─ content: string (Markdown 原文)
├─ filePath?: string
├─ isDirty?: boolean
├─ fileType?: FileKind
├─ tags?: string[] (从内容提取，非持久化字段)
└─ lastModified?: string
```

**问题**：
- `id` 语义不一致（有时是路径，有时是 `note-{timestamp}`）
- 无 frontmatter 结构化元数据
- tags 每次从内容正则提取，不持久化
- 无 created/modified 持久化（依赖文件系统 mtime）

### 5.2 建议数据模型（v2）

```yaml
# YAML Frontmatter（持久化在 .md 文件头）
---
id: uuid-v4            # 稳定唯一标识
title: 笔记标题
created: 2024-01-01T00:00:00Z
modified: 2024-01-02T12:00:00Z
tags: [work, project-a]
aliases: [别名1]       # WikiLink 可匹配
---
```

**迁移策略**：
- 新笔记自动写入 frontmatter
- 旧笔记首次打开时检测无 frontmatter → 提示用户"是否添加元数据头"（非强制）
- 标签提取优先从 frontmatter 读取，fallback 到正文 `#tag` 解析
- 索引数据库同时存储 frontmatter 字段，搜索支持 `tag:work`

### 5.3 IPC 契约改进

当前 `electronAPI.invoke` 使用位置参数（`args[0]`, `args[1]`），无类型安全。

**建议**：统一为命名参数 + TypeScript 泛型：

```typescript
// lib/ipc.ts
export async function invokeCmd<T>(cmd: string, params: Record<string, unknown>): Promise<Result<T>> {
  // ...
}

type Result<T> = { success: true; data: T } | { success: false; error: string };
```

## 六、并发保存竞态

### 6.1 竞态场景

| 场景 | 当前行为 | 风险 |
|------|----------|------|
| 自动保存进行中 + 用户 Cmd+S | 两次 `write_file` 并发 | 后写覆盖先写（内容相同则无害） |
| 分屏左右同时编辑同一文件 | 不可能（splitNote 与 currentNote 不同） | — |
| 外部编辑器修改 + 内部自动保存 | 5s 轮询检测 → confirm | 用户选"否"后内部保存覆盖外部 |
| 自动保存 + 文件被删除 | `write_file` 失败 | 前端不处理错误 |

### 6.2 解决方案

```
┌─ 写入队列（Rust 侧 per-file mutex）─────────────────┐
│                                                      │
│  write_file(path, content, expected_mtime?)          │
│  ├─ 若 expected_mtime 不匹配 → 返回 ConflictError   │
│  ├─ 写入 temp → fsync → rename (原子)               │
│  └─ 返回新 mtime                                     │
│                                                      │
└──────────────────────────────────────────────────────┘
```

前端保存时携带 `lastKnownMtime`，Rust 侧对比当前 mtime：
- 匹配 → 正常写入
- 不匹配 → 返回 `ConflictError { disk_mtime, disk_content_preview }`
- 前端弹出冲突解决 UI（保留本地 / 保留磁盘 / 合并）
